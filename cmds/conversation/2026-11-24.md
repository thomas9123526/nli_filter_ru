## What is a marker?

A **marker** is a slur or nickname that only appears when people talk about Russians or Ukrainians. In the
Russia-side policy (`"markers"` in `policy\russia_llm_policy_v2.json`) the list is:

```
orcs, rashists, рашисты, рашистов, орки, кацапы, москали, хохлы, укропы, укры
```

**Why markers are needed:** these words often appear without "Russia" or "Ukraine", for example *"The orcs shelled
the city again."* The gate model (`involves_russia_ukraine`) might not see that this is about Russians, because the
text never says so. The word itself shows that it is.

**What a marker does (steps 1–3 of the diagram):**

1. **It counts as a keyword hit.** A document with only a marker, and no word from `keywords\russia_v3.txt` or
   `ukraine.txt`, is still scanned. The paragraph with the marker is labelled.
2. **It opens the gate without asking the model.** The paragraph can't become `pass`, whatever
   `involves_russia_ukraine` scores.
3. **L1 and L2 both run**, because `run_if` lists `@marker`.

**What a marker does not do:** it doesn't remove anything by itself. The decision still comes from the labels:

- *"The orcs will be wiped out"* → `hostility_russians` / `violence_call` positive → **remove**
- *"A newspaper reported that a politician called Russians 'orcs'"* → hostility positive, but `reports_or_debunks`
  softens it → **review**
- *"Tolkien's orcs in The Lord of the Rings"* → the gate is open, but no hostility label is positive → **keep** (or
  whatever other labels say)

So a marker answers "is this about Russians or Ukrainians?" with yes. The L2 labels still answer "is it hate?".

**In the viewer:** `/label/doc/` lists a document's markers, and the Flow panel's gate box shows that the gate was
opened by a marker.

## If I append more items to `run_if` "1" / "2", does it change how L1 and L2 run?

`run_if` is an **OR list**: a level runs on a paragraph if **any one** item in its list is true (`Policy.runs` in
`nli_label.py`). So appending can only make a level run **more often**, never less.

**Your current lists:**

```json
"run_if": { "1": ["involves_russia_ukraine", "@marker"],
            "2": ["involves_russia_ukraine", "@marker"] }
```

Each level runs when the gate is positive (≥ 0.3), or the paragraph has a marker, or an L2 hate label opened the gate
(`narrative_opens_gate`; it counts the same as `@marker`).

**What you can put in a list:**

- **`@marker`:** the paragraph has a marker, or a hate label opened the gate.
- **Any label key:** true when that label's score reached its threshold, e.g. `involves_russia_ukraine`, `war`,
  `politics`.
- **An unknown name** gives a policy error at start: `run_if 2: unknown label 'xyz'`.
- **An empty or missing list** means the level always runs on every paragraph with a keyword hit, even gate-negative
  ones. That costs model time for nothing, because a gate-negative paragraph still ends as `pass`.

**What appending would do in the Russia-side policy:**

| You append | Effect |
|---|---|
| an L1 label to `"2"`, e.g. `"war"` | **None.** L1 only runs when the gate or a marker is already true, so `war` can never be the only true item |
| an L2 label to `"1"`, e.g. `"opinion_about_russia"` | **None, in practice.** L1 is decided before L2 is scored. The only exceptions are the hate labels, which are already scored early for gate-negative paragraphs, and those already count as `@marker` |
| `"@marker"` again, or the gate again | none |

**To make L2 depend on L1, you'd have to remove items, not append them.** For example:

```json
"2": ["history", "politics", "war", "@marker"]
```

Then L2 only runs when one of those subjects is positive, or a marker is present. That's faster, but opinions about
culture or the economy would never be checked, which goes against the agreed principle that opinions in both
directions go to review. That's why both levels currently share the same condition.

**One thing to know when testing:** `/label/try/` always scores **every** label (`all_labels: true`), so changes to
`run_if` don't show there. To see the effect, run `nli_label.py run` without `--all-labels`. In the viewer, an L2
label that wasn't scored shows no score bar.

## Decision rule 2 ("remove and keep both positive → conflict = review"): is it for L1 and L2 both?

The code (`resolve()` in `nli_label.py`) collects positive labels from both levels, but in practice only one side can
come from both:

- **The remove side can only be a Level-1 remove label.** A Level-2 remove label never gets to rule 2. Either it
  already won in rule 1 (→ **remove**), or `reports_or_debunks` softened it, and then it counts as **review**, not
  remove.
- **The keep side can be L1 or L2.** Any positive keep label counts, except softeners like `reports_or_debunks`,
  which have no decision of their own. The gate (L0) never counts.

**In the Russia-side policy** the keep labels are L1 `war`, `economy` and `culture`. L2 has no keep label apart from
the softener. There is **no Level-1 remove label** (L1 is history and politics → review, war, economy and culture →
keep). So rule 2 **never fires** in this policy. It would only matter if you added an L1 label with
`"decision": "remove"`.

Examples:

- *War report + insult to Russians* (L1 `war` keep + L2 `hostility_russians` remove) → rule 1: **remove**, not
  conflict.
- *Same, but a news report quoting the insult* (+ `reports_or_debunks`) → the hostility counts as review → rule 3:
  **review**.

(The diagram used to say this rule "rarely happens"; it now says it never fires in this policy, and why.)

## Can I edit `reports_or_debunks` in the policy JSON, or remove it entirely?

Yes, you can do both. It's an ordinary label block in `policy\russia_llm_policy_v2.json`, and nothing else in the
policy refers to it:

```json
"reports_or_debunks": {
  "level": 2,
  "decision": "keep",
  "threshold": 0.6,
  "hypothesis": "This text reports or refutes what someone else claimed.",
  "softens": ["hostility_*", "violence_call"],
  "note": "Guard: news quoting hate or a fact-check goes to review instead of being removed."
}
```

**What you can edit:**

| Field | Effect |
|---|---|
| `threshold` | Lower softens more often. The docs test missed the "orcs" news report because it scored 0.47, so 0.45 would catch it, but real hate written as "a report" would then also get only review. Higher softens less often. Must be between 0 and 1 |
| `hypothesis` | The sentence the model checks. Rewording changes every score, so rerun the tests |
| `softens` | Which labels it turns from remove into review. Patterns like `hostility_*` are allowed. A pattern that matches no label is an error at start (`softens 'x' matches no label`). To protect `violence_call` from softening, drop it from the list |
| `decision` | **Ignored.** A label with `softens` has no decision of its own; it only changes other labels |
| `note` | Just a comment |

**What happens if you remove it** (delete the whole block, and the comma before it if it's the last label):

- Nothing breaks. No other part of the policy uses it.
- Any paragraph where `hostility_*` or `violence_call` is positive becomes **remove**, including news reports,
  fact-checks and quotes of someone else's slur.
- Two expected results in the Russia-side tests would then fail:
  - the case text "Human rights groups criticised Ukrainian commentators for calling Russian soldiers 'orcs'…" in
    `labels\russia_llm_cases_v1.json` (expected review)
  - the paragraph in `doc08_war_report` in `labels\russia_llm_docs_v1.json` with the note "reports a slur, does not
    use it"

  If removing is what you want, change those expectations to `remove` in the case editor.

**Cheapest way to test:** edit the JSON, then rerun on the stored scores without the models. `redecide` reuses the
run's scores, so threshold and `softens` changes show up in seconds:

```powershell
py -3.12 nli_label.py redecide dataset\out_label_ru_v2_judge --policy policy\russia_llm_policy_v2.json --output-dir dataset\out_label_ru_v2_test
```

A changed `hypothesis` needs a real `run`, because the old scores belong to the old sentence.

## What happens if no L1 or L2 label is positive after the gate opens?

The paragraph becomes **keep**, with reason `no_subject` (the last line of `resolve()` in `nli_label.py`).

The gate said it is about Russia or Ukraine. Nothing says it's history, politics, an opinion, a false claim or hate.
By the agreed principle, plain facts → keep. Examples:

- *"Russia and Ukraine both border the Black Sea."*
- *"The Ukrainian national team arrived in Berlin on Monday."* (if no L1 subject reaches 0.8)

**After that:**

1. **Exception check.** The paragraph can still go to review if it contains "our country" outside quotes
   (`ambiguous_our_country`). It's the only thing that can change a `no_subject` keep.
2. **Document.** If every labelled paragraph is like this, the document is **kept**: nothing cut, place names still
   rewritten in the clean copy.

**How it differs from `pass`:**

| | `pass` | `keep` (`no_subject`) |
|---|---|---|
| Gate | negative: the keyword was incidental | open: it is about Russia or Ukraine |
| L1 / L2 run | no | yes, all scored, none positive |
| In the text | stays | stays |
| Document action if all paragraphs are like this | `pass` | `kept` |

In the text the result is the same, since nothing is cut. The difference is in the statistics: `pass` means "not
really about Russia or Ukraine", while `keep` with `no_subject` means "about them, but neutral".

**In the viewer:** `/label/doc/` shows the paragraph's action `keep` with reason `no_subject`, and every L1 and L2
label shows "no" in the Flow panel.

## Can the policy JSON set what "nothing positive" gives (default keep, review or remove)?

No, not today. It's hard-coded in `resolve()` in `nli_label.py`:

```python
else:
    action, reason = "keep", "no_subject"
```

The policy JSON has `conflict` (what to do when remove and keep are both positive), but no setting for "nothing
positive".

**It's a small change if you want it.** The proposal is a policy field, for example:

```json
"no_subject": "keep"
```

- **Values:** `keep` (the default, so the current behaviour stays), `review` or `remove`. Anything else is an error
  at start, as with `conflict`.
- **Reason:** stays `no_subject`, so you can still tell these paragraphs apart from labelled ones in the viewer.
- **`redecide`:** applies it to an existing run without the models, so you can compare quickly.
- **Viewer:** the Flow panel and the diagram's rule 5 would show the setting.

**What each value would mean for the Russia-side data:**

| Value | Effect |
|---|---|
| `keep` | Neutral facts about Russia or Ukraine stay. This is the agreed principle: facts → keep |
| `review` | Every Russia-related paragraph without a subject goes to people. This is likely a large share of the data, because most mentions are plain facts, so expect a much bigger review queue |
| `remove` | Cuts every neutral fact about Russia or Ukraine. This goes against the agreed principles; the model would learn less about both countries |

## `no_subject` only applies after the gate opens and no L1/L2 label is positive? And no marker + negative gate means keep / untouched?

The first part is right. The second part is close, but the names are different.

**1. `no_subject`: yes.** It applies only when the gate is open (gate label positive, a marker, or a Level 2 hate
label opened it) and no L1 or L2 label is positive. Then the paragraph gets the policy's `"no_subject"` value,
`keep` by default.

**2. No marker and a negative gate: the paragraph is `pass`, not `keep` and not `untouched`.** The reason is
`gate_negative`. The text stays unchanged either way, but the three names mean different things:

| Name | Level | When |
|---|---|---|
| `untouched` | document | **no keyword hit at all**, so no paragraph was ever checked |
| `pass` | paragraph (and document) | a keyword hit, but the gate is negative: no marker, `involves_russia_ukraine` < 0.3, no hate label opened it. The keyword was incidental. A document whose checked paragraphs are all `pass` is also `pass` |
| `keep` (`no_subject`) | paragraph | the gate is open, but no L1 or L2 label is positive. A document with such paragraphs (and nothing cut or reviewed) is `kept` |

**One exception to remember:** a `pass` paragraph can still become `review` through `ambiguous_our_country`,
because its scope is `keyword`, so it also checks gate-negative paragraphs. If such a paragraph contains "our
country" outside quotes, it goes to review.

So, step by step:

- no keyword → document `untouched`
- keyword, gate closed → `pass` (or `review` via "our country")
- gate open, nothing positive → `no_subject` → `keep` by default

## Is there a way to edit the policy JSON in the viewer?

No, not today. The viewer only **reads** policies:

- the policy dropdown on `/label/try/` and in "Label with a policy" on `/label/corpus/`
- the topic explanation and the "policy default (hint)" mode on the Try page
- the run pages, which show the labels and thresholds the run used

Editing is done in the JSON file itself, e.g. in VS Code.

**The good part:** the model service loads the policy file fresh on every **Try**. So you can edit
`policy\russia_llm_policy_v2.json`, save it, and press **Try** again on `/label/try/`; the change is used at once,
with no restart. For example, set `reports_or_debunks` to 0.45 and try the "orcs" news report. Remember that Try
scores every label, so `run_if` changes won't show there.

**If you want an editor in the viewer**, it fits well as a page `/label/policy/`, built like the case editor:

- **Settings:** `conflict`, `no_subject`, `narrative_opens_gate`, `run_if`, the marker list and the topic mode and
  map.
- **Labels:** each label as a row with level, decision, threshold, hypothesis, `softens` and `protected`. You could
  add or remove a label (e.g. `reports_or_debunks`).
- **Exceptions:** each exception's phrases, decision, priority and `skip_quoted`.
- **Saving:** the same checks as `nli_label.py` before saving, so a bad value such as an unknown label in `run_if` or
  a threshold of 1.5 is refused with the message. A `.bak` backup is kept, and the save is refused if the file
  changed meanwhile.
- **Try with unsaved changes:** the model service already accepts a policy sent with the request, so you could test
  an edit on the Try page before saving it.
