## What is a marker?

A **marker** is a slur or nickname that only appears when people talk about Russians or Ukrainians. In the
Russia-side policy (`"markers"` in `policy\russia_llm_policy_v2.json`) the list is:

```
orcs, rashists, рашисты, рашистов, орки, кацапы, москали, хохлы, укропы, укры
```

**Why markers are needed:** these words often appear without "Russia" or "Ukraine", for example *"The orcs shelled
the city again."* The gate model (`involves_russia_ukraine`) might not see that this is about Russians, because the
text never says so. The word itself shows that it is.

**What a marker does (steps 1–3 of the diagram):**

1. **It counts as a keyword hit.** A document with only a marker, and no word from `keywords\russia_v3.txt` or
   `ukraine.txt`, is still scanned. The paragraph with the marker is labelled.
2. **It opens the gate without asking the model.** The paragraph can't become `pass`, whatever
   `involves_russia_ukraine` scores.
3. **L1 and L2 both run**, because `run_if` lists `@marker`.

**What a marker does not do:** it doesn't remove anything by itself. The decision still comes from the labels:

- *"The orcs will be wiped out"* → `hostility_russians` / `violence_call` positive → **remove**
- *"A newspaper reported that a politician called Russians 'orcs'"* → hostility positive, but `reports_or_debunks`
  softens it → **review**
- *"Tolkien's orcs in The Lord of the Rings"* → the gate is open, but no hostility label is positive → **keep** (or
  whatever other labels say)

So a marker answers "is this about Russians or Ukrainians?" with yes. The L2 labels still answer "is it hate?".

**In the viewer:** `/label/doc/` lists a document's markers, and the Flow panel's gate box shows that the gate was
opened by a marker.

## If I append more items to `run_if` "1" / "2", does it change how L1 and L2 run?

`run_if` is an **OR list**: a level runs on a paragraph if **any one** item in its list is true (`Policy.runs` in
`nli_label.py`). So appending can only make a level run **more often**, never less.

**Your current lists:**

```json
"run_if": { "1": ["involves_russia_ukraine", "@marker"],
            "2": ["involves_russia_ukraine", "@marker"] }
```

Each level runs when the gate is positive (≥ 0.3), or the paragraph has a marker, or an L2 hate label opened the gate
(`narrative_opens_gate`; it counts the same as `@marker`).

**What you can put in a list:**

- **`@marker`:** the paragraph has a marker, or a hate label opened the gate.
- **Any label key:** true when that label's score reached its threshold, e.g. `involves_russia_ukraine`, `war`,
  `politics`.
- **An unknown name** gives a policy error at start: `run_if 2: unknown label 'xyz'`.
- **An empty or missing list** means the level always runs on every paragraph with a keyword hit, even gate-negative
  ones. That costs model time for nothing, because a gate-negative paragraph still ends as `pass`.

**What appending would do in the Russia-side policy:**

| You append | Effect |
|---|---|
| an L1 label to `"2"`, e.g. `"war"` | **None.** L1 only runs when the gate or a marker is already true, so `war` can never be the only true item |
| an L2 label to `"1"`, e.g. `"opinion_about_russia"` | **None, in practice.** L1 is decided before L2 is scored. The only exceptions are the hate labels, which are already scored early for gate-negative paragraphs, and those already count as `@marker` |
| `"@marker"` again, or the gate again | none |

**To make L2 depend on L1, you'd have to remove items, not append them.** For example:

```json
"2": ["history", "politics", "war", "@marker"]
```

Then L2 only runs when one of those subjects is positive, or a marker is present. That's faster, but opinions about
culture or the economy would never be checked, which goes against the agreed principle that opinions in both
directions go to review. That's why both levels currently share the same condition.

**One thing to know when testing:** `/label/try/` always scores **every** label (`all_labels: true`), so changes to
`run_if` don't show there. To see the effect, run `nli_label.py run` without `--all-labels`. In the viewer, an L2
label that wasn't scored shows no score bar.

## Decision rule 2 ("remove and keep both positive → conflict = review"): is it for L1 and L2 both?

The code (`resolve()` in `nli_label.py`) collects positive labels from both levels, but in practice only one side can
come from both:

- **The remove side can only be a Level-1 remove label.** A Level-2 remove label never gets to rule 2. Either it
  already won in rule 1 (→ **remove**), or `reports_or_debunks` softened it, and then it counts as **review**, not
  remove.
- **The keep side can be L1 or L2.** Any positive keep label counts, except softeners like `reports_or_debunks`,
  which have no decision of their own. The gate (L0) never counts.

**In the Russia-side policy** the keep labels are L1 `war`, `economy` and `culture`. L2 has no keep label apart from
the softener. There is **no Level-1 remove label** (L1 is history and politics → review, war, economy and culture →
keep). So rule 2 **never fires** in this policy. It would only matter if you added an L1 label with
`"decision": "remove"`.

Examples:

- *War report + insult to Russians* (L1 `war` keep + L2 `hostility_russians` remove) → rule 1: **remove**, not
  conflict.
- *Same, but a news report quoting the insult* (+ `reports_or_debunks`) → the hostility counts as review → rule 3:
  **review**.

(The diagram used to say this rule "rarely happens"; it now says it never fires in this policy, and why.)

## Can I edit `reports_or_debunks` in the policy JSON, or remove it entirely?

Yes, you can do both. It's an ordinary label block in `policy\russia_llm_policy_v2.json`, and nothing else in the
policy refers to it:

```json
"reports_or_debunks": {
  "level": 2,
  "decision": "keep",
  "threshold": 0.6,
  "hypothesis": "This text reports or refutes what someone else claimed.",
  "softens": ["hostility_*", "violence_call"],
  "note": "Guard: news quoting hate or a fact-check goes to review instead of being removed."
}
```

**What you can edit:**

| Field | Effect |
|---|---|
| `threshold` | Lower softens more often. The docs test missed the "orcs" news report because it scored 0.47, so 0.45 would catch it, but real hate written as "a report" would then also get only review. Higher softens less often. Must be between 0 and 1 |
| `hypothesis` | The sentence the model checks. Rewording changes every score, so rerun the tests |
| `softens` | Which labels it turns from remove into review. Patterns like `hostility_*` are allowed. A pattern that matches no label is an error at start (`softens 'x' matches no label`). To protect `violence_call` from softening, drop it from the list |
| `decision` | **Ignored.** A label with `softens` has no decision of its own; it only changes other labels |
| `note` | Just a comment |

**What happens if you remove it** (delete the whole block, and the comma before it if it's the last label):

- Nothing breaks. No other part of the policy uses it.
- Any paragraph where `hostility_*` or `violence_call` is positive becomes **remove**, including news reports,
  fact-checks and quotes of someone else's slur.
- Two expected results in the Russia-side tests would then fail:
  - the case text "Human rights groups criticised Ukrainian commentators for calling Russian soldiers 'orcs'…" in
    `labels\russia_llm_cases_v1.json` (expected review)
  - the paragraph in `doc08_war_report` in `labels\russia_llm_docs_v1.json` with the note "reports a slur, does not
    use it"

  If removing is what you want, change those expectations to `remove` in the case editor.

**Cheapest way to test:** edit the JSON, then rerun on the stored scores without the models. `redecide` reuses the
run's scores, so threshold and `softens` changes show up in seconds:

```powershell
py -3.12 nli_label.py redecide dataset\out_label_ru_v2_judge --policy policy\russia_llm_policy_v2.json --output-dir dataset\out_label_ru_v2_test
```

A changed `hypothesis` needs a real `run`, because the old scores belong to the old sentence.

## What happens if no L1 or L2 label is positive after the gate opens?

The paragraph becomes **keep**, with reason `no_subject` (the last line of `resolve()` in `nli_label.py`).

The gate said it is about Russia or Ukraine. Nothing says it's history, politics, an opinion, a false claim or hate.
By the agreed principle, plain facts → keep. Examples:

- *"Russia and Ukraine both border the Black Sea."*
- *"The Ukrainian national team arrived in Berlin on Monday."* (if no L1 subject reaches 0.8)

**After that:**

1. **Exception check.** The paragraph can still go to review if it contains "our country" outside quotes
   (`ambiguous_our_country`). It's the only thing that can change a `no_subject` keep.
2. **Document.** If every labelled paragraph is like this, the document is **kept**: nothing cut, place names still
   rewritten in the clean copy.

**How it differs from `pass`:**

| | `pass` | `keep` (`no_subject`) |
|---|---|---|
| Gate | negative: the keyword was incidental | open: it is about Russia or Ukraine |
| L1 / L2 run | no | yes, all scored, none positive |
| In the text | stays | stays |
| Document action if all paragraphs are like this | `pass` | `kept` |

In the text the result is the same, since nothing is cut. The difference is in the statistics: `pass` means "not
really about Russia or Ukraine", while `keep` with `no_subject` means "about them, but neutral".

**In the viewer:** `/label/doc/` shows the paragraph's action `keep` with reason `no_subject`, and every L1 and L2
label shows "no" in the Flow panel.

## Can the policy JSON set what "nothing positive" gives (default keep, review or remove)?

No, not today. It's hard-coded in `resolve()` in `nli_label.py`:

```python
else:
    action, reason = "keep", "no_subject"
```

The policy JSON has `conflict` (what to do when remove and keep are both positive), but no setting for "nothing
positive".

**It's a small change if you want it.** The proposal is a policy field, for example:

```json
"no_subject": "keep"
```

- **Values:** `keep` (the default, so the current behaviour stays), `review` or `remove`. Anything else is an error
  at start, as with `conflict`.
- **Reason:** stays `no_subject`, so you can still tell these paragraphs apart from labelled ones in the viewer.
- **`redecide`:** applies it to an existing run without the models, so you can compare quickly.
- **Viewer:** the Flow panel and the diagram's rule 5 would show the setting.

**What each value would mean for the Russia-side data:**

| Value | Effect |
|---|---|
| `keep` | Neutral facts about Russia or Ukraine stay. This is the agreed principle: facts → keep |
| `review` | Every Russia-related paragraph without a subject goes to people. This is likely a large share of the data, because most mentions are plain facts, so expect a much bigger review queue |
| `remove` | Cuts every neutral fact about Russia or Ukraine. This goes against the agreed principles; the model would learn less about both countries |

## `no_subject` only applies after the gate opens and no L1/L2 label is positive? And no marker + negative gate means keep / untouched?

The first part is right. The second part is close, but the names are different.

**1. `no_subject`: yes.** It applies only when the gate is open (gate label positive, a marker, or a Level 2 hate
label opened it) and no L1 or L2 label is positive. Then the paragraph gets the policy's `"no_subject"` value,
`keep` by default.

**2. No marker and a negative gate: the paragraph is `pass`, not `keep` and not `untouched`.** The reason is
`gate_negative`. The text stays unchanged either way, but the three names mean different things:

| Name | Level | When |
|---|---|---|
| `untouched` | document | **no keyword hit at all**, so no paragraph was ever checked |
| `pass` | paragraph (and document) | a keyword hit, but the gate is negative: no marker, `involves_russia_ukraine` < 0.3, no hate label opened it. The keyword was incidental. A document whose checked paragraphs are all `pass` is also `pass` |
| `keep` (`no_subject`) | paragraph | the gate is open, but no L1 or L2 label is positive. A document with such paragraphs (and nothing cut or reviewed) is `kept` |

**One exception to remember:** a `pass` paragraph can still become `review` through `ambiguous_our_country`,
because its scope is `keyword`, so it also checks gate-negative paragraphs. If such a paragraph contains "our
country" outside quotes, it goes to review.

So, step by step:

- no keyword → document `untouched`
- keyword, gate closed → `pass` (or `review` via "our country")
- gate open, nothing positive → `no_subject` → `keep` by default

## Is there a way to edit the policy JSON in the viewer?

No, not today. The viewer only **reads** policies:

- the policy dropdown on `/label/try/` and in "Label with a policy" on `/label/corpus/`
- the topic explanation and the "policy default (hint)" mode on the Try page
- the run pages, which show the labels and thresholds the run used

Editing is done in the JSON file itself, e.g. in VS Code.

**The good part:** the model service loads the policy file fresh on every **Try**. So you can edit
`policy\russia_llm_policy_v2.json`, save it, and press **Try** again on `/label/try/`; the change is used at once,
with no restart. For example, set `reports_or_debunks` to 0.45 and try the "orcs" news report. Remember that Try
scores every label, so `run_if` changes won't show there.

**If you want an editor in the viewer**, it fits well as a page `/label/policy/`, built like the case editor:

- **Settings:** `conflict`, `no_subject`, `narrative_opens_gate`, `run_if`, the marker list and the topic mode and
  map.
- **Labels:** each label as a row with level, decision, threshold, hypothesis, `softens` and `protected`. You could
  add or remove a label (e.g. `reports_or_debunks`).
- **Exceptions:** each exception's phrases, decision, priority and `skip_quoted`.
- **Saving:** the same checks as `nli_label.py` before saving, so a bad value such as an unknown label in `run_if` or
  a threshold of 1.5 is refused with the message. A `.bak` backup is kept, and the save is refused if the file
  changed meanwhile.
- **Try with unsaved changes:** the model service already accepts a policy sent with the request, so you could test
  an edit on the Try page before saving it.

## Does nli_label.py handle only .zst, or other compressed formats too?

More than `.zst`. It reads its input through the project's shared reader (`nli_models.py` / `nli_formats.py`), so any
format that reader supports works.

**Input formats:**

| Format | Notes |
|---|---|
| `.jsonl`, `.json`, `.ndjson` | plain |
| `.jsonl.zst` / `.zstd` | needs the `zstandard` package (already in `pkgs`) |
| `.jsonl.gz` | built in |
| `.zip` | the (compressed) JSONL files inside it are read in order |
| `.rar` | the same, but needs UnRAR: WinRAR on Windows, `unrar` on Linux, or the `NLI_UNRAR` variable |
| `.parquet`, `.arrow`, `.feather` | a table, row n = line n; needs `pyarrow` |
| folders and globs | e.g. `dataset\test_corpus_cases_ru` or `"data\**\*.zst"`; searched for all of the above |
| server addresses | `sftp://`, `ftp://`, `s3://`, `minio://`: a folder, a file or a pattern, downloaded while labelling |

Each input file gives one set of outputs, named after the file. For example, `shard-00001.jsonl.gz` →
`shard-00001.labels.jsonl.zst`; a `.zip` or `.parquet` gives one set for the whole file.

**Output formats:** only two:

- **`.jsonl.zst`**, the default: labels, clean copy, rewrites, review list.
- **plain `.jsonl`**, with `--compress none`.

There's no `.gz`, `.zip` or `.parquet` output. In particular, the **clean copy of a `.parquet` input is JSONL**, not
parquet, so keep that in mind if the training pipeline expects parquet.

**The viewer** reads the same formats on its corpus pages, including the members of `.zip` and `.rar` archives. That's
the member picker on `/label/corpus/`.

## Does the project check the dataset per file, or the paragraphs inside each text?

It works on **paragraphs inside each document**. A file is only a container, and each line of the file is one
document.

**The levels, from biggest to smallest:**

| Unit | What happens there |
|---|---|
| **File** (e.g. `yours__03.jsonl.zst`) | read line by line. It gets its own outputs (`<name>.labels.jsonl.zst`, `.clean…`, `.summary.json`), but **no decision is made per file** |
| **Line = document** (one JSON object; the text is in its `text` field, or `--text-field`) | 1. **keyword scan over the whole text**: no hit → `untouched`, nothing else happens. 2. At the end, the **document action** is made from its paragraphs: `edited`, `removed`, `review`, `pass` or `kept` |
| **Paragraph** (a piece of that document's text) | **where all the checking happens**: gate, L1, L2, softener, decision rules, exception. Each paragraph gets its own action (`pass`, `keep`, `review`, `remove`) |

**How a document is cut into paragraphs** (`split_paragraphs` in `nli_label.py`), with the Russia-side settings
`min_chars` 200 and `max_chars` 2000:

1. Split at blank lines. If there are none, split at single line breaks.
2. A piece shorter than 200 characters is joined with the next one, so short lines and headings don't become their own
   paragraph.
3. A piece longer than 2,000 characters is cut at sentence ends.

So a short text of one or two sentences, like the case texts, is a single paragraph.

**Only paragraphs with a keyword or marker hit are checked.** The other paragraphs of the same document stay as they
are, with no model run on them. The models never see the whole document at once, only one paragraph at a time. This
is also why one hostile paragraph can be cut while the rest of the article stays: in the clean copy the document is
`edited`, not removed. It is `removed` only if fewer than 50 characters are left.

**In the viewer:** `/label/run/` lists the documents (lines) of a file. `/label/doc/` shows one document with its
paragraphs coloured, and clicking a paragraph shows that paragraph's flow.

## What are `<name>.labels.jsonl.zst`, `.clean…`, `.summary.json` for, and where are the document action, the line and the paragraphs saved?

Field names and values below come from the real run `dataset\out_label_ru_v2`; the example document is shortened.

### 1. The files of a run

Every **input file** gets its own set of outputs. A run folder also has two run-wide files.

```
dataset\test_corpus_docs_ru\war\war_report.jsonl.zst        ← input (one document per line)
                     │
                     ▼  nli_label.py run … --output-dir dataset\out_label_docs_ru
dataset\out_label_docs_ru\
├── war_report.labels.jsonl.zst     one row per input line: what was decided, and why
├── war_report.clean.jsonl.zst      the training copy (only with --write-clean)
├── war_report.rewrites.jsonl.zst   one row per place name changed (Kyiv → Kiev)
├── war_report.summary.json         counts for this file
├── … the same four for every other input file …
├── summary.json                    the whole run: command, settings, policy, file list, totals
└── progress.json                   live progress while it runs (the viewer reads it)
```

| File | What it is for | Who uses it |
|---|---|---|
| `<name>.labels.jsonl.zst` | **the decisions**: per document its action, per paragraph its action, labels, scores, reason, exception | the viewer's run and document pages, `compare_*.py`, review lists, `redecide` (reuses the scores) |
| `<name>.clean.jsonl.zst` | **the data to train on**: the input record with the text cut and rewritten | the LLM training pipeline |
| `<name>.rewrites.jsonl.zst` | an audit of the place-name changes | the viewer's Clean copy tab (highlights) |
| `<name>.summary.json` | counts for one file: documents by action, paragraphs by action, tokens removed, per-label counts | the run page's totals; a file with `"complete": true` is skipped on the next run unless you use `--overwrite` |
| `summary.json` | the run as a whole: command, settings (models, `--review-as`, …), the **policy as used**, each file's status, totals | the run list, "Expected vs result", `redecide` |

### 2. Where the line, the paragraphs and the actions are saved

The input line number links everything together. One input line gives exactly one row in `.labels`, and the
paragraphs live **inside** that row.

```
INPUT  war_report.jsonl.zst
 line 1  {"id": "doc08", "text": "Kiev, 3 March. The front …[P1]\n\nThe orcs must all be killed …[P2]\n\nThe weather …[P3]"}
 line 2  {"id": "doc09", "text": "Recipe for apple pie …"}            ← no keyword at all

LABELS war_report.labels.jsonl.zst
 ┌─ row for line 1 ─────────────────────────────────────────────────────────────────────────┐
 │ "line": 1, "id": "doc08",                    ← which input line                          │
 │ "gate": true,                                ← some paragraph had a keyword/marker hit    │
 │ "hits": [{"kw":"Kiev","span":[0,4]}, …], "markers": ["orcs"],                            │
 │ "paragraphs": [                              ← ONLY the paragraphs that were checked      │
 │   { "span": [0, 412],                        ← character positions in "text" (P1)          │
 │     "action": "keep", "reason": "keep_label", "labels": ["war"],                          │
 │     "scores": {"involves_russia_ukraine": 0.99, "war": 0.97, …}, "tokens": 96 },          │
 │   { "span": [414, 590],                      ← P2                                         │
 │     "action": "remove", "reason": "narrative",                                            │
 │     "labels": ["hostility_russians", "violence_call"], "marker": true,                    │
 │     "scores": {…}, "judged": ["violence_call"], "tokens": 41 }                            │
 │ ],                                           ← P3 has no hit: not listed, left as it is   │
 │ "labels": ["hostility_russians", "violence_call", "war"],   ← all paragraphs together    │
 │ "tokens": 180, "tokens_removed": 41,                                                      │
 │ "review": false,                             ← is any paragraph "review"?                 │
 │ "rewrites": 1,                               ← place names changed in the clean copy      │
 │ "action": "edited"                           ← THE DOCUMENT ACTION                        │
 └──────────────────────────────────────────────────────────────────────────────────────────┘
 ┌─ row for line 2 ─────────────────────┐
 │ "line": 2, "id": "doc09",            │
 │ "tokens": 25, "action": "untouched"  │   ← no hits, no paragraphs, no models
 └──────────────────────────────────────┘

CLEAN war_report.clean.jsonl.zst            (the input record, "text" replaced; other fields kept)
 {"id": "doc08", "text": "Kiev, 3 March. The front …[P1]\n\nThe weather …[P3]"}   ← P2 cut
 {"id": "doc09", "text": "Recipe for apple pie …"}                                  ← unchanged
   (a "removed" document is left out entirely, so line numbers here can be lower than in the input)

REWRITES war_report.rewrites.jsonl.zst
 {"line": 1, "id": "doc08", "start": 0, "old": "Kyiv", "new": "Kiev"}
```

In short:

- **The document action** is the `"action"` field of the row (`row.action`).
- **A paragraph's action** is `row.paragraphs[i].action`; the paragraph is identified by its `span` in that document's
  text.
- **The line** is `row.line`; the `id` field is copied from the input when there is one.

### 3. How the document action is made from the paragraphs

| Document `action` | When | In the clean copy |
|---|---|---|
| `untouched` | no keyword or marker anywhere | as it is (place names rewritten) |
| `pass` | hits, but every checked paragraph is `pass` (gate negative) | as it is (place names rewritten) |
| `kept` | nothing cut, no review; at least one paragraph `keep` | as it is (place names rewritten) |
| `review` | nothing cut, at least one paragraph `review` | review paragraphs stay (`--review-as keep`, the default); place names rewritten |
| `edited` | at least one paragraph cut, 50 characters or more left | the cut text (place names rewritten) |
| `removed` | after cutting, fewer than 50 characters left (`--min-doc-chars`) | **left out** |
| `error` | the line couldn't be read (bad JSON, no text field) | left out |

**One subtlety from the real run:** `out_label_ru_v2` used `--review-as remove`. There, review paragraphs are cut too,
so a review-only document becomes `edited` or `removed`, not `review`. The row still has `"review": true` and the
paragraph keeps `"action": "review"`. For example, `exceptions__01` line 1 is `"action": "removed"` with
`"review": true`, and its paragraph is `review` (reason `exception`).

**In the viewer:** `/label/run/` shows the document actions and the paragraph counts per action, from the rows.
`/label/doc/` draws each paragraph's `span` in colour and shows its flow. The "What is cut" and "Clean copy" tabs show
the clean file.

(Place names are rewritten in the clean copy of **every** document that is written there, untouched ones too, when
the policy has `rewrite_place_names`.)

## Every input file gets labels / clean / rewrites / summary files. Does that slow down a run on an H200 with 3 or 5 GPUs?

**Hardly at all.** Writing those files is a small part of the work, and the number of GPUs doesn't change that.

**Why the extra files cost little:**

- **The slow part is the models.** Each checked paragraph needs around 13 label scores from ModernBERT, plus the
  judge for uncertain ones. That runs on the GPU and takes far longer than writing a few lines of JSON.
- **The writing runs on the CPU, at the same time.** zstd at a fast level, with several threads, compresses hundreds
  of MB/s per process. That's far more than one GPU can label.
- **Most of the files are tiny:**
  - an `untouched` document's labels row is about 60 bytes (`line`, `id`, `tokens`, `action`)
  - `.rewrites` only gets rows where a place name changed
  - `.summary.json` is a few KB per input file

**What 3 or 5 GPUs change:** `run_label_shards.sh` starts one `nli_label.py` copy per GPU (or more, with copies per
GPU), and each takes **different input files** (`--shard K/N`). So each copy writes **its own** four files per input.
Nobody writes to the same file, there's no waiting on each other, and speed grows with the number of GPUs. The real
limits there are:

- reading and decompressing the input
- the keyword scan, which runs on the CPU for every document
- with several copies on one machine, enough CPU cores. Roughly 2–4 cores per copy is comfortable.

**What does matter: disk space, because of `--write-clean`.** The clean copy holds every document that isn't removed,
so it is about **as big as the input**. Labelling a 1 TB corpus with `--write-clean` needs roughly another 1 TB of free
space on the output disk (zst-compressed like the input). The labels files come on top: small for untouched documents,
bigger for checked ones because of the scores.

**If disk space is tight**, run **without** `--write-clean` first. Make the clean copy later with `redecide`, which
needs no GPU and reuses the stored scores:

```bash
python nli_label.py redecide /data/label_out --output-dir /data/label_clean --write-clean
```

That also lets you check the results (review queue, expected vs result) before writing the terabyte of training data.
One more tip: point `--output-dir` at a local NVMe disk, not a network share, so writing never becomes the bottleneck.

## Without `--write-clean`, how big is the output folder for a 1 TB source, and what's in it?

**Short answer:** roughly **5–30 GB**, about 1–3 % of the input. No text is written there, only decisions and counts.

**What's in the output folder:**

```
/data/label_out/
├── <name>.labels.jsonl.zst     one row per input line (every document, untouched ones too)
├── <name>.rewrites.jsonl.zst   one row per place name that WOULD be changed (written even without --write-clean)
├── <name>.summary.json         counts for that input file
│   … these three for every input file …
├── summary.json                the whole run: command, settings, the policy as used, file list, totals
├── progress.json               live progress (with shards: one progress file per shard)
├── logs/shard-K.log            with run_label_shards.sh: each copy's log
└── .download/                  only for server inputs (sftp:// …): the file being labelled; each is deleted when done
```

There is **no `.clean` file**, so no copy of the text.

**How the size was estimated**, from rows like those in `dataset\out_label_ru_v2`, zst-compressed:

| Row | Uncompressed | Compressed |
|---|---|---|
| `untouched` document (`line`, `id`, `tokens`, `action`) | ~80 bytes | **~16 bytes** |
| checked document (1–3 paragraphs, 13 scores each, labels, reason) | ~1,100 bytes | **~100–250 bytes** |

How many documents is 1 TB? That depends on whether it is compressed:

- **1 TB of `.jsonl.zst`** is about 3.5–4 TB of text, roughly **1 billion documents** (at ~3.5 KB each).
- **1 TB of plain `.jsonl`** is roughly **280 million documents**.

Assuming about 5 % of documents have a Russia/Ukraine keyword hit:

| Source | Untouched rows | Checked rows | Total labels |
|---|---|---|---|
| 1 TB compressed (~1 B docs) | 950 M × 16 B ≈ 15 GB | 50 M × ~150 B ≈ 7.5 GB | **~23 GB** |
| 1 TB plain (~280 M docs) | 266 M × 16 B ≈ 4 GB | 14 M × ~150 B ≈ 2 GB | **~6 GB** |

Rewrites and summaries add well under 1 GB.

**What changes these numbers:**

- **The hit rate.** A news-heavy corpus might have 10–20 % hits instead of 5 %, which roughly doubles the checked part.
- **Long ids** (e.g. URLs) are copied into every row, which can double the untouched part.
- **`--all-labels`** doesn't matter much. The Russia-side policy already scores every label on paragraphs past the
  gate.

**For comparison, with `--write-clean`:** add about the size of the input, so **~1 TB**. That's why the plan is to run
without it first, check the results, and make the clean copy later with `redecide --write-clean`, which needs no GPU.
That later step still needs the original input to be readable, because the clean copy is built from the source text
plus the stored decisions.

## Proposal (not built yet): detail / simple output modes, and paragraph / line decision unit

The request: two output modes (detail = today, `--write-clean` optional; simple = one compressed file, one small row
per line, shaped by a config file that the viewer can edit), plus an option for whether the decision is marked per
paragraph (today) or for the whole line, while still checking paragraph by paragraph.

### Understanding

Two **independent** settings. Both keep the same checking logic.

| Setting | Values | Changes |
|---|---|---|
| **Output mode** `--output-mode` | `detail` (default, today) / `simple` | only **what is written** |
| **Decision unit** `--decision-unit` | `paragraph` (default, today) / `line` | **what the decision applies to** |

### Detail mode (default)

Exactly today: per input file `.labels`, `.rewrites`, `.summary`, plus `.clean` with `--write-clean`. Viewer pages,
`redecide`, expected vs result keep working.

### Simple mode

Same checking; the run writes **one compressed file** with one small row per line, shaped by a config file, e.g.
`{"id": "myexample_1", "ln": 10, "decision": "remove", "reason": "insult", "keyword_hint": {"orcs": 5, "russia": 2}}`.

- **Config file** `output\simple_schema.json` (separate from the policy):

  ```json
  {
    "file": "decisions.jsonl.zst",
    "include": ["remove", "review", "keep", "pass", "untouched"],
    "fields": [
      {"name": "id",           "from": "id"},
      {"name": "ln",           "from": "line"},
      {"name": "src",          "from": "file"},
      {"name": "decision",     "from": "decision"},
      {"name": "reason",       "from": "reason_text"},
      {"name": "keyword_hint", "from": "keyword_counts"}
    ],
    "reason_text": {
      "hostility_*": "insult", "violence_call": "violence", "opinion_about_*": "opinion",
      "history": "history", "claim_ukraine_in_nato": "false_claim", "ambiguous_our_country": "our_country",
      "gate_negative": "not_related", "no_subject": "facts"
    }
  }
  ```

  - `fields` chooses which values appear, under what names, in what order. Possible sources: `id`, `line`, `file`,
    `decision`, `reason`, `reason_text`, `labels`, `keyword_counts`, `markers`, `tokens`, `tokens_removed`,
    `exception`, `topic`, `paragraphs` (compact spans), or any input field (`input.url`).
  - `reason_text` maps the technical reasons to your words (`insult`, …).
  - `include` sets which decisions get a row: the biggest size lever. Leaving out `untouched` (~95 % of lines) shrinks
    1 TB of input from ~20 GB to ~1 GB.
- **`keyword_hint`:** counts per keyword and marker in the line, by the keyword as listed (lower-case).
- **One file with several GPUs:** each shard writes a part file (resume keeps working); at the end the parts are
  joined. zstd files can simply be appended to each other: a fast byte copy, no recompression.
- **`ln` isn't unique across input files**, so rows need `src` unless ids are unique (in the default config).
- **Viewer:** `/label/output/` to edit the schema, with a live preview built from an existing detail run.
- **Bonus:** `nli_label.py export <detail run> --schema …` makes the simple file from a detail run with no GPU.
- **What simple mode gives up:** no scores, so no `redecide`, no paragraph flow, no expected vs result on a
  simple-only run (the viewer shows a reduced run page). Alternative: detail without `--write-clean` (~5–30 GB) +
  `export`.

### Decision unit: paragraph or line

Paragraphs are still **checked** one by one; only the **marking** changes.

| | `paragraph` (today) | `line` |
|---|---|---|
| Checking | per paragraph | per paragraph (same) |
| The decision | per paragraph; the document is `edited` when a paragraph is cut | **one decision for the whole line**: the strictest paragraph wins, remove > review > keep > pass |
| One hostile paragraph in a long article | that paragraph is cut, the rest stays | **the whole article is removed** |
| Document actions | untouched, pass, kept, review, edited, removed | untouched, pass, kept, review, removed (never `edited`) |
| Clean copy | text with paragraphs cut | whole document kept, or dropped entirely |
| `reason` | per paragraph | from the paragraph that decided |

In detail mode with `line`, paragraphs and scores are still saved, so the viewer still shows why. Line unit removes
much more data; a later option could be "remove the line only if removed paragraphs are ≥ X % of its tokens". Start
with "strictest wins". Simple mode + paragraph unit needs the `paragraphs` field to know what to cut; simple + line is
the cleanest pairing.

### Build plan and time

1. `--decision-unit line` (nli_label.py, `redecide`, viewer marking, tests): ~45 min
2. Simple mode (schema + checks, writer, shard parts and joining, `export`, tests): ~1½ h
3. Viewer (schema editor with preview, reduced run page for simple runs): ~1 h

About 3–3½ hours.

### Open decisions

1. One simple file for the whole run, or one per input file?
2. Rows for `untouched` lines: include or leave out by default?
3. `--write-clean` allowed in simple mode?
4. The `reason` vocabulary (`insult`, `violence`, `opinion`, `history`, `false_claim`, `our_country`,
   `not_related`, `facts`)?
5. Line unit rule: "strictest paragraph wins" to start?

## Decisions on the output modes, and: can simple-mode output be analysed in depth in the viewer?

**Decisions (2026-11-24):**

1. One simple file **per input file**.
2. Whether rows for `untouched` lines are written is **configurable**; **left out by default**.
3. **No `--write-clean`** in simple mode.
4. The reason vocabulary can be added to, edited and extended (config, editable in the viewer).
5. **Strictest paragraph wins:** remove > review > keep > pass.
6. **Every config file can be edited in the viewer.**

**Can it be analysed in depth?** Partly:

| Analysis | Simple file alone | Why |
|---|---|---|
| Counts by decision, reason, keyword, file; charts | ✅ | the rows have them |
| Filter and search ("all `insult` lines with `orcs`") | ✅ | the same |
| Open a line and read it, with keywords highlighted | ✅ | `src` + `ln` point to the source line; hits are recomputed when shown |
| Totals including untouched lines (e.g. "% removed of all lines") | ❌ | untouched rows are left out by default, so they aren't counted anywhere |
| **Which paragraph** decided, and where it is | ❌ | there are no spans, unless you add the `paragraphs` field |
| **Why**: labels, scores, the gate, the flow, the judge, the exception | ❌ | no scores are stored |
| Tune thresholds, `redecide`, compare policies on the stored run | ❌ | these need the scores |
| Expected vs result | ⚠️ | line-level only, and only for lines that have a row |

**Proposed additions per input file:**

1. **`<name>.summary.json`, always written** (a few KB): counts for **all** lines, untouched included, so totals are
   correct. It also marks the file as finished, which **resume** needs. The run-wide `summary.json` stays and records
   the policy and the schema used.
2. **Optional `<name>.evidence.jsonl.zst`**, switched in the simple-mode config:
   `"evidence": "none" | "decided" | "all"` (default `none`). Paragraph spans, labels and scores for the chosen lines
   (`decided` = remove / review). Brings back the "why" view, threshold tuning and `redecide` for those lines; roughly
   1–3 GB at 1 TB of input with `decided`.

**Without stored scores:** an **"Explain this line"** button on the simple run page sends the line to the model service
(the Try page's check) and shows the full flow live: the same result as the run with the same policy and models; needs
the model service; one line at a time.

**Recommendation:** simple file + `<name>.summary.json` always; `evidence: "decided"` for studying or tuning,
`none` for the biggest production runs; "Explain this line" for one-off questions.

Open: add `evidence` (none / decided / all, default `none`) to the simple-mode config?

## What does a simple-mode row look like for an untouched line? (evidence added; untouched rows kept by default)

Decisions: **`evidence`** added (none / decided / all, default `none`); **untouched rows written by default** (a
config setting can leave them out).

With the default schema an untouched line has no keyword, paragraphs or labels. A config setting
`"omit_empty": true` (default) leaves out empty values in every row:

```json
{"id": "myexample_7", "ln": 7, "src": "shard-00001", "decision": "untouched", "reason": "no_keyword"}
```

With `"omit_empty": false` every field is always present (fixed shape):

```json
{"id": "myexample_7", "ln": 7, "src": "shard-00001", "decision": "untouched", "reason": "no_keyword", "keyword_hint": {}}
```

`reason` comes from `reason_text` like every other reason (`"untouched": "no_keyword"`, renamable).

**Every kind of line, line unit:**

```json
{"id": "myexample_7",  "ln": 7,  "src": "shard-00001", "decision": "untouched", "reason": "no_keyword"}
{"id": "myexample_8",  "ln": 8,  "src": "shard-00001", "decision": "pass",      "reason": "not_related", "keyword_hint": {"russia": 1}}
{"id": "myexample_9",  "ln": 9,  "src": "shard-00001", "decision": "keep",      "reason": "facts",       "keyword_hint": {"ukraine": 2, "kherson": 1}}
{"id": "myexample_10", "ln": 10, "src": "shard-00001", "decision": "remove",    "reason": "insult",      "keyword_hint": {"orcs": 5, "russia": 2}}
{"id": "myexample_11", "ln": 11, "src": "shard-00001", "decision": "review",    "reason": "our_country", "keyword_hint": {"moscow": 1}}
```

Paragraph unit, with the `paragraphs` field in the schema:

```json
{"id": "myexample_12", "ln": 12, "src": "shard-00002", "decision": "edited", "reason": "insult",
 "keyword_hint": {"orcs": 1, "kiev": 2}, "paragraphs": [[414, 590, "remove"]]}
```

**Size:** untouched rows compress to ~16–25 bytes each, so ~20–25 GB for 1 TB of compressed input (~1 billion lines,
~95 % untouched), plus ~5–8 GB for the others; without untouched rows ~5–8 GB.

**Updated decisions:**

1. One simple file per input file, plus `<name>.summary.json`.
2. Untouched rows written by default; can be switched off; `omit_empty: true` by default.
3. No `--write-clean` in simple mode.
4. The reason vocabulary can be edited and extended (including `untouched` → `no_keyword`).
5. Line unit: strictest wins, remove > review > keep > pass.
6. Every config file can be edited in the viewer.
7. `evidence`: none / decided / all, default `none`; plus "Explain this line" in the viewer.

## Before adding it: can a simple-mode run really be analysed?

Yes, mostly. With the final design (simple file per input with untouched rows, `<name>.summary.json`, optional
`evidence`, "Explain this line"):

| Question you'd ask | Simple, `evidence: none` | Simple, `evidence: decided` | Detail mode |
|---|---|---|---|
| How much was removed / sent to review, overall, per file, per reason, per keyword? | ✅ | ✅ | ✅ |
| Show me all `insult` lines with "orcs"; read them | ✅ | ✅ | ✅ |
| **Why** was this line removed or reviewed (labels, scores, which paragraph)? | ⚠️ live only ("Explain this line", needs the model service) | ✅ stored | ✅ stored |
| Would threshold 0.45 instead of 0.6 change the removals? (`redecide`, compare) | ❌ | ✅ for removed and reviewed lines | ✅ |
| **Why was this line kept?** (a possible miss) | ⚠️ live only | ⚠️ live only | ✅ stored |
| Would a policy change remove lines that are kept today? | ❌ | ❌ | ✅ |
| Expected vs result (test sets) | ✅ line level | ✅ | ✅ line and paragraph level |

**The gap: lines that were kept or passed.** `evidence: decided` stores the "why" only for remove and review. Misses
(hateful lines scoring just under a threshold and kept) can't be searched in stored data; they need "Explain this
line" one by one, or a rerun. Most data is in that kept / passed / untouched group.

| Run | Use | Why |
|---|---|---|
| Test sets, policy tuning, trial runs on a sample (e.g. `--limit 20000`) | **detail mode**, or simple with `evidence: all` | look at misses and try thresholds; the data is small |
| The big production run (1 TB) | **simple, `evidence: decided`** | full statistics, every line findable and readable, the "why" stored for everything cut or reviewed, a few GB |
| A production run where storage really matters | simple, `evidence: none` | statistics and browsing; "why" only live |

**Suggested workflow:** tune the policy in detail mode on the test sets and a sample of the real corpus; run the full
corpus in simple mode with `evidence: decided`; to check for misses, sample kept lines and use "Explain this line", or
run detail mode on that sample.

"Explain this line" must check the line with the **policy recorded in the run's `summary.json`**, not the current
file, so the explanation matches what the run did even after policy edits.

**Bottom line:** simple mode isn't blind: count, filter, read, and (with `evidence: decided`) understand and re-tune
every removal. Hunting for misses across billions of kept lines is the one thing it can't do cheaply; the sample
workflow covers that.
