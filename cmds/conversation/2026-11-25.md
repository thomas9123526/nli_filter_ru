## Q: (not this project, about speed) TopicClassifier on H200 × 8 GPUs: how long for 10T parquet?

This is a back-of-envelope estimate, not measured. It reads "10T" as **10 TB of parquet files**.

**Assumptions**

- Data size:
  - 10 TB of parquet holds about 25 TB of raw text (compression of 2–3×).
  - That is about 6T tokens (about 4 bytes per token).
  - At about 5 KB per document, it is about 5B documents.
- Model cost:
  - The model is small (about 140M parameters), roughly 0.2 GFLOP per token.
- Speed per H200:
  - Tuned (bf16, flash attention, no padding, batches sorted by length): about 1M tokens/s.
  - Plain `transformers` pipeline with padding: about 0.25M tokens/s.

**Estimated time on 8 × H200**

| What is classified | Tokens | Tuned (≈ 8M tok/s) | Plain pipeline (≈ 2M tok/s) |
|---|---|---|---|
| First 256 tokens per doc | ≈ 1.2T | **≈ 1.7 days** | ≈ 7 days |
| First 512 tokens per doc | ≈ 2.2T | **≈ 3 days** | ≈ 13 days |
| Whole docs (up to 8192 tokens) | ≈ 6T + attention cost | ≈ 11 days | ≈ 45 days |

**What decides the time**

1. **Truncation.** A topic is decided from the start of a document. The cost then follows the number of documents,
   not the bytes.
2. **Padding and batching.** Avoiding wasted padding makes the run 3–5× faster.
3. **The CPU side.** Reading parquet is cheap. Tokenizing about 8M tokens/s needs about 8–16 CPU cores. Cut the text
   to about 3000 characters before tokenizing.

If "10T" means 10T **tokens**, multiply the times by about 1.7.

**The reliable way:** time one GPU on a sample of about 100k real documents, then multiply.

## Q: what is the difference between tuned code and plain pipeline?

Both run the same model and give the same answers. The difference is only how well the GPU is kept busy. The speeds
(about 1M vs 0.25M tokens/s per H200) are my estimates, not measured.

| | Plain pipeline | Tuned code |
|---|---|---|
| Call | `pipeline("text-classification", ...)` or a simple loop | own loop with `AutoModelForSequenceClassification` |
| Precision | often fp32 (slow) | `torch_dtype=torch.bfloat16` |
| Padding | every text padded to the longest in the batch | `unpad_inputs=True`: no padding is computed |
| Attention | standard | `use_memory_efficient_attention=True` (flash-style) |
| Batching | arbitrary order, small batches | texts sorted by length, big batches (e.g. 64–256) |
| Tokenizing | in the same process, GPU waits | separate CPU workers, GPU never waits |
| GPUs | one process, one GPU | one process per GPU, each on its own files |

Where the gain comes from (rough): bf16 about 2×, no padding about 2×, sorted + large batches about 1.5×, overlapping
CPU and GPU the rest. Together about 4×.

The model card shows the tuned settings for this model: `unpad_inputs=True, use_memory_efficient_attention=True,
torch_dtype=torch.bfloat16`.

## Q: how to use tuned code? does the source code provide it?

Checked on 2026-11-25 in `annotate_data/domains.py` and `annotate.sh` of github.com/CodeCreator/WebOrganizer.

The repo gives a **partly tuned** script, not the fully tuned code:

| Tuning item | In the repo's script? |
|---|---|
| bf16 | yes (`model.to(torch.bfloat16)`) |
| Tokenizing in separate CPU workers | yes (DataLoader, `num_workers=8`, `prefetch_factor=4`) |
| Large batches | yes (default `batch_size=128`) |
| Unpadded inputs / memory-efficient attention | **no** (the model is loaded without `unpad_inputs` or `use_memory_efficient_attention`) |
| Sorting by length | **no** (`shuffle=False`, per-batch padding) |
| Several GPUs in one process | **no** (`model.cuda()` = one GPU) |
| Several GPUs / machines | via SLURM array jobs: one job per GPU, each takes every N-th file |

Input and output go through the `datatools` library (`load`, `process`), which was not read.

How to use it:
1. Use it as a base, or write the loop yourself from the model card (below).
2. Add `unpad_inputs=True, use_memory_efficient_attention=True, torch_dtype=torch.bfloat16` to `from_pretrained(...,
   trust_remote_code=True)`.
3. Sort a chunk of documents by length before batching.
4. Start one process per GPU (`CUDA_VISIBLE_DEVICES=i`), each on its own files (file number % number of GPUs). For
   5 machines: file number % 40.

## Q: Does it use xFormers? does it involve a tokenizer? if so, the tokenizer unit size for tuned code?

Checked on 2026-11-25: `config.json`, `tokenizer_config.json` and `tokenizer.json` of WebOrganizer/TopicClassifier, and
`modeling.py` of Alibaba-NLP/new-impl (the model's code, read in part).

**xFormers: yes.**
- The model's `config.json` already sets `"use_memory_efficient_attention": true` and `"unpad_inputs": true`.
- With these settings, attention runs through `xformers.ops.memory_efficient_attention`. Unpadding uses xFormers'
  `BlockDiagonalMask`.
- If xFormers is not installed, loading fails with the assertion "please install xformers". There is no automatic
  fallback.
- To run without xFormers, load with `use_memory_efficient_attention=False`, as the model card's simple example does.
  That is slower.
- **Correction to the previous answer.** The repo's script `domains.py` loads the model without overriding these
  settings, so it **does** use unpadding and xFormers, taken from `config.json`. It still does not sort by length and
  uses one GPU per run.
- Not checked: the gte-base-en-v1.5 card says newer `transformers` (5.18+) runs this model natively, with SDPA or
  Flash Attention 2 and without the custom code. Whether the TopicClassifier checkpoint works that way was not checked.

**Tokenizer: yes.** It is a `BertTokenizer`, the same as bert-base-uncased:
- WordPiece subwords (`##` for word pieces), lowercased.
- Vocabulary: about 30.5K entries (`vocab_size: 30528` in config.json).
- Special tokens `[CLS]` and `[SEP]` are added: 2 per document.
- Unit size: 1 token ≈ 4–4.5 characters of English text, about 0.75 words. Non-English text splits into many more
  tokens, and non-Latin scripts often become `[UNK]`.
- Length per document in tuned code: up to **8192 tokens** (the authors' setting), about 33–37K characters of English.
  Cutting the text to about 40K characters before tokenizing saves CPU without changing the result.
- Watch out: `tokenizer.json` itself has truncation 512 and fixed padding 512. `transformers` replaces this with what
  you pass in the call. If you use the `tokenizers` library directly (`Tokenizer.from_file`), it would cut at 512 and
  pad every document to 512. Set `max_length=8192` explicitly.

## Q: with 5 machines, how many sentences/tokens are processed in parallel at each step (tokenizer, then topic)?

**The unit is a document, not a sentence.** The classifier reads `url + "\n\n" + text` as one input, up to 8192 tokens,
and gives one topic per document. Nothing is split into sentences.

**The flow for one GPU process** (as in the repo's `domains.py`):

```
parquet file ──► read rows ──► CPU workers: build "{url}\n\n{text}", tokenize, make batches
   (disk)        (main proc)    (DataLoader, 8 workers, each does one batch of 128 docs)
                                      │  queue: up to 8 × 4 = 32 ready batches (prefetch_factor 4)
                                      ▼
                     GPU: one batch at a time
                     embeddings → 12 transformer layers → [CLS] vector → linear head → 24 logits
                                      ▼
                     CPU: argmax / softmax → write {logits, choice} per document
```

All tokens of a batch go through each layer together. With unpadding, the batch is one long row of tokens, and
xFormers' block-diagonal mask keeps the documents from seeing each other.

**How much is in flight.** Repo defaults (batch 128 docs, 8 workers, prefetch 4); about 1250 tokens per doc on
average; tuned speed of about 1M tokens/s per GPU.

| Step | Per GPU process | Per machine (8 GPUs) | 5 machines (40 GPUs) |
|---|---|---|---|
| CPU workers tokenizing | 8 workers × 128 = 1,024 docs | 64 workers, 8,192 docs | 320 workers, 40,960 docs |
| Tokenized batches waiting | up to 32 batches = 4,096 docs | 32,768 docs | 163,840 docs |
| On the GPU at once | 1 batch = 128 docs ≈ 160K tokens (at most 128 × 8192 ≈ 1M) | 1,024 docs ≈ 1.3M tokens | 5,120 docs ≈ 6.4M tokens |
| Finished per second | ≈ 800 docs (a batch every ≈ 0.16 s) | ≈ 6,400 docs | ≈ 32,000 docs ≈ 40M tokens |
| CPU cores needed | 9 (8 workers + main) | 72 | 360 |

The GPU step is the bottleneck. The CPU side only has to keep the queue from running empty, which is why there are
8 workers and prefetching.

**For tuned code:** with document lengths from 50 to 8192 tokens, a fixed 128 documents per batch varies from about
6K to 1M tokens. It is better to batch by a token budget (for example about 256K–512K tokens per batch; the H200 has
141 GB), with documents sorted by length. The numbers above are estimates, not measured.

## Q: also want know how they affect speed

The rule: **the run goes as fast as its slowest step.** The GPU should be the slowest step and should stay busy. Every
other setting either keeps the GPU fed or wastes GPU work. Effects are rough estimates, not measured.

**Settings that change the GPU's own speed**

| Setting | Effect on speed | Why |
|---|---|---|
| bf16 instead of fp32 | about 2× faster | the H200's tensor cores are built for bf16 |
| Unpadding (`unpad_inputs`) | about 1.5–3× faster | without it, the GPU computes padding up to the longest document of the batch |
| xFormers attention | about 1.2–2× faster, more for long documents | attention cost grows with length²; the memory-efficient kernel is faster and uses much less memory |
| Sorting by length | small with unpadding (≈ 1.1×), large without it (≈ 2×) | similar lengths mean little padding and even batches |
| Batch size / token budget | too small: GPU half idle; past ≈ 100K–500K tokens: no further gain | a big batch keeps all GPU cores busy; beyond that the GPU is already full. Too big means out of memory |
| `max_length` (8192 vs 512 vs 256) | biggest single lever: 512 is about 2–3× faster, 256 about 4–5× | fewer tokens to compute; long documents also cost more per token (attention ∝ length²) |

**Settings that keep the GPU fed** (no gain once the GPU is fed; a big loss if not)

| Setting | Effect on speed | Why |
|---|---|---|
| Tokenizer workers (`num_workers`) | too few: the GPU waits. 8 per GPU is usually enough at ≈ 1M tokens/s | one fast tokenizer worker handles roughly 0.2–0.5M tokens/s |
| Prefetch (`prefetch_factor`) | smooths out slow moments (a long document, a slow file read) | ready batches wait in a queue |
| CPU cores | fewer than workers per machine: everything slows | 8 GPUs × 9 = 72 cores per machine |
| Cutting text before tokenizing (≈ 40K chars) | saves CPU on very long documents | tokenizing text that would be thrown away anyway |
| Disk / network reading | small: 4 TB per day is ≈ 50 MB/s | only a problem on slow shared storage |
| Writing results | small, if written in big chunks | 24 numbers per document |

**Settings that multiply**

| Setting | Effect on speed |
|---|---|
| More GPUs / machines | nearly linear (40 GPUs ≈ 40×), since every GPU works on its own files |
| Uneven files | the job ends when the **last** GPU ends. Use many small files, or hand files out from a queue |

**How to tell what is slow** (on a test run):
- `nvidia-smi` shows GPU use **above 90%**: the GPU is the limit, which is good. Make it faster with bf16, unpadding,
  xFormers or a shorter `max_length`.
- GPU use **jumps up and down** or stays **below 70%**: the CPU side is too slow. Add workers or prefetch, or check
  the CPU with `top`.
- **Out of memory**: lower the batch or token budget.

## Q: if one document has over 8192 tokens (e.g. 50000), does it read the first 8192 or split it and process all pieces?

**It reads the first 8192 and drops the rest. Nothing is split.** One document still gets one topic.

- The authors' script (`domains.py`) calls the tokenizer with `truncation=True, max_length=8192`. The tokenizer's
  `truncation_side` is `"right"`, so the end is cut off.
- The 8192 includes `[CLS]`, `[SEP]` and the URL line. That leaves about 8190 tokens for URL + text, about 33–37K
  characters of English. Of a 50,000-token document, tokens 8191–50,000 (about 84%) are never seen.
- The URL is at the front, so it is always kept.
- The model card's simple example passes no truncation. A 50,000-token input would be sent to the model whole. The
  model was built and trained for 8192 positions (`max_position_embeddings: 8192`), so that is either an error or an
  untrained case. Not tested. Always pass `truncation=True, max_length=8192`.

If the whole document should count, splitting must be added by hand:
1. Cut the text into pieces of about 8000 tokens and put the URL before each piece.
2. Classify each piece.
3. Combine the results, for example by averaging the 24 probabilities (weighted by piece length), or by keeping the
   pieces' topics separately.

The authors did not do this. It costs more because every token is computed. Documents above 8192 tokens are usually a
small share of web data, so the first 8192 tokens are normally enough to decide the topic.

## Q: how many sentences and how many words are 8192 tokens?

For ordinary English web text with this tokenizer (lowercased BERT WordPiece). These are rules of thumb, not measured
on your data:

| | About |
|---|---|
| Words | **6,000–6,300** (≈ 1.3 tokens per word; punctuation counts as its own token) |
| Sentences | **300–400** (at 15–20 words per sentence) |
| Characters | 33,000–37,000 |
| Printed pages | about 12 (500 words per page) |
| Paragraphs | about 80–120 (60–80 words each) |

Text that needs more tokens, so fewer words fit:
- code, URLs, numbers, tables, rare names and technical words: about 1.5–2 tokens per word, so 4,000–5,500 words;
- other languages: many more tokens, and non-Latin scripts often become `[UNK]`.

To measure it on your data: `len(tokenizer(text)["input_ids"])` against `len(text.split())` on a sample.

| Documents with a keyword | Per 1 TB of text (one machine) | **4 TB parquet on 5 machines** |
|---|---|---|
| 1 % | ≈ 1.5 h | **≈ 4 hours** |
| 3 % | ≈ 3–4 h | **≈ 7–10 hours** |
| 10 % | ≈ 10–12 h | **≈ 1–1¼ days** |

- `--judge-model none` saves about 20–40 % of GPU time but changes decisions (2 wrongly removed on the cases).
- `--write-clean` adds writing a copy about the size of the input.
- The real corpus' keyword share is not known yet. A news- or politics-heavy corpus can be well above 10 %.

**5 machines:** `run_label_shards.sh` splits the work only within one machine. Give each machine its own fifth of the

**To get the real figure:** one sizing run on one machine (`--limit 20000`, section 4 of `nli_label_h200.md`), then
`full hours ≈ run_seconds × (corpus lines ÷ stats.lines) ÷ 3600 ÷ 5`. The run's `summary.json` also gives the keyword
share (`stats.docs.untouched`).

## Q: do I have to use run_label_shards.sh for 5 machines? if so, what is the guide to get full speed?

**No, it is not required.** It is a launcher for **one** machine. It starts `GPUs × copies per GPU` copies of
`nli_label.py run`, each with `--shard k/N`, where N is the number of copies on that machine. It does not know about
other machines. Checked in `run_label_shards.sh` and `nli_label.py`. `--shard K/N` takes every N-th file of the
**sorted** file list, so the same list on every machine gives the same split.

### Two ways to use 5 machines

**A. Split the files into 5 folders, then run the script on each machine** (simplest):
```bash
# machine m (0..4), its own folder and its own output folder on a local disk
./run_label_shards.sh /data/corpus_part$m /data/label_out_m$m 2 \
    --policy policy/russia_llm_policy_v2.json --batch-size 256 --chunk-lines 256 --write-clean
```
Risk: if the 5 folders are not equal in size, the run waits for the biggest one.

**B. One shared corpus path, one global split over all 80 copies** (no folders to prepare; the files are spread
evenly). Every machine must see the same files under the same path (a shared mount, or identical copies). Instead of the
script, run this on each machine with its own `M`:
```bash
M=0                      # this machine: 0,1,2,3,4
MACHINES=5; GPUS=8; PER_GPU=2
N=$((MACHINES * GPUS * PER_GPU))            # 80 copies in total
OUT=/data/label_out_m$M; mkdir -p $OUT/logs
for ((i = 0; i < GPUS * PER_GPU; i++)); do
  k=$((M * GPUS * PER_GPU + i)); g=$((i % GPUS))
  python nli_label.py run /data/corpus --device cuda:$g --shard $k/$N --output-dir $OUT \
      --policy policy/russia_llm_policy_v2.json --batch-size 256 --chunk-lines 256 --write-clean \
      > $OUT/logs/shard-$k.log 2>&1 &
done
wait; python nli_label.py report $OUT
```
Use one output folder per machine on a local disk, not one shared network folder. Each machine gives its own
`report`, so there are 5 reports.

### Guide to full speed (per machine)

1. **Sizing run first:** the same command with `--limit 20000` into a test folder, on one machine. It gives the speed,
   the keyword share and the time (`nli_label_h200.md` section 4).
2. **Copies per GPU: 2.** Use 3 if `nvidia-smi` shows GPU use under 50 %. One copy reads and keyword-scans on one CPU
   core (about 40 MB/s), which cannot keep an H200 busy alone.
3. **`--batch-size 256`**, raise to 512 while lines/s improves and memory is under 70 %. Halve it on out-of-memory.
4. **`--chunk-lines 256–512`**: bigger chunks make fuller GPU batches.
5. **Many files of similar size:** sharding is per file. Have at least several files per copy (80 copies → hundreds
   of files). One huge file keeps one copy running long after the rest.
6. **Disks:** output on a fast local disk. Input on local disk or a fast mount. For server input, `--download-dir` on a
   fast disk.
7. **CPU and memory:** 16–24 copies per machine need as many free CPU cores, plus RAM for 16–24 model copies.
8. **Judge:** keep it on for the real run. If judge pairs are more than 25 % of fast pairs, consider
   `--uncertain-band 0.6 0.9` (check the cases first).
9. **Resume:** if a copy fails, run the same command again; finished files are skipped.

## Q: is batch-size related to the CPU and chunk-lines to the GPU, when reading nvidia-smi?

**Not quite. Both act on the GPU side. The CPU lever is the number of copies per GPU.** Checked in `nli_label.py`.

How one copy works:
1. The CPU reads `--chunk-lines` lines (default 64), keyword-scans them and splits paragraphs.
2. All (paragraph, hypothesis) pairs of the chunk go to the model, in GPU calls of `--batch-size` pairs.
3. Results are written, then the next chunk is read. With one GPU per copy this is one step after the other, so while
   the CPU reads, the GPU of that copy waits.

| Setting | What it is | What it changes |
|---|---|---|
| `--batch-size` | pairs per GPU call | GPU **memory** and how full each GPU call is |
| `--chunk-lines` | lines read before scoring | how many pairs exist to fill the batches. Only a few % of lines have a keyword: 64 lines × 3 % ≈ 2 documents ≈ a few dozen pairs, far below a batch of 256. So 256–512 lines are needed to fill the batches |
| copies per GPU | processes sharing one GPU | **CPU** reading/scanning in parallel, and covers the gaps while one copy reads |

Reading `nvidia-smi`:

| You see | Cause | Change |
|---|---|---|
| GPU use low (< 50 %) | GPU waits for reading/scanning | **more copies per GPU** (3); then `--chunk-lines` up |
| GPU use high, memory < 70 % | GPU busy, memory to spare | `--batch-size` up (512) |
| memory full / out of memory | batches too big (× copies on the GPU) | `--batch-size` down |

A bigger `--batch-size` only helps if the chunk has enough pairs to fill it. Raise `--chunk-lines` together with it.

## Q: is "memory" GPU memory or normal RAM? how to see the changes in nvidia-smi?

**In the tuning tables, "memory" means GPU memory** (VRAM, 141 GB per H200). `--batch-size` and the number of copies
per GPU change it. Normal RAM is not shown by `nvidia-smi`.

**Reading `nvidia-smi`** (one table per GPU, plus a process list at the bottom):

```
| GPU  Name        ...  |  Memory-Usage          | GPU-Util |
|   0  NVIDIA H200 ...  |  38211MiB / 143771MiB  |    92%   |   <- GPU 0: memory used / total, busy share
...
| Processes:                                              |
|   0   N/A  N/A  12345  C  python   18900MiB             |   <- each copy and its GPU memory
|   0   N/A  N/A  12346  C  python   19100MiB             |
```

- **GPU-Util**: the share of time the GPU was busy. This is "GPU use" in the tables (low = waiting for the CPU side).
- **Memory-Usage**: GPU memory used out of the total. This is "memory" (< 70 % = room for a bigger `--batch-size`).
- **Processes**: one line per copy. 2 copies per GPU = 2 `python` lines per GPU.

Watching it during the run:
```bash
nvidia-smi -l 5          # the full table every 5 seconds
nvidia-smi --query-gpu=index,utilization.gpu,memory.used,memory.total --format=csv -l 5   # one line per GPU
nvidia-smi dmon -s um    # running log: utilization (u) and memory (m) per GPU, one line per second
```

Notes:
- GPU-Util jumps between chunks. Watch it for a minute, not one snapshot.
- PyTorch keeps GPU memory it has used once, so Memory-Usage shows roughly the **peak**. After changing
  `--batch-size`, restart the copies and compare after a few minutes.
- Running out shows as `CUDA out of memory` in `OUTPUT_DIR/logs/shard-K.log`.

**Normal RAM** (CPU memory): each copy holds its models, a chunk of lines and the output buffers. Watch it with
`free -h` or `htop`. Running out of RAM shows as a copy that was "Killed" (check `dmesg | tail`), not as a CUDA error.
Then use fewer copies.

## Q: a diagram of how CPU memory and GPU memory are used (copies, processes, copies per GPU, one line per copy, 8 × H200, 5 machines), plus commands to watch GPU, CPU and memory on Ubuntu H200 and Windows 10 RTX 5090

Answered with the page `cmds/h200/copies_and_memory.html`, also published at
https://claude.ai/artifact/CVFQ5Lgne6kyJ1NezRKsWS.

**Terms**
- A copy is one `nli_label.py run`. That is one process, one `--shard k/80`, one log file and one line in
  `nvidia-smi`'s process list.
- Copy k uses GPU k mod 8.
- 2 copies per GPU × 8 GPUs = 16 copies per machine. × 5 machines = 80 copies.

**Memory per copy** (estimates, not measured)

- GPU memory: about 4–8 GB at `--batch-size 256`.

- One machine: about 50–100 GB of RAM.

**Watching GPU, CPU and memory**
- Ubuntu:
  - GPU: `nvidia-smi -l 5`, `nvidia-smi dmon -s um`.

  - If installed: `htop`, `nvtop`, `nvitop`.
- Windows 10:
  - GPU: `nvidia-smi -l 5`.
  - Task Manager → Performance → GPU, with the graph set to "Cuda" or "Compute_0".

## Q: does the 4 TB speed estimate depend on nli_label's arguments (detail/simple mode, others)?

**Yes, it does.** The estimate assumed the recommended run: the Russia-side v2 policy, ModernBERT plus the DeBERTa
judge, 2 copies per GPU, `--batch-size 256`, `--chunk-lines 256`, `--write-clean`. Detail and simple mode **do not
exist yet**; they are in the plan `11_24_output_modes`.

**Large effect: changes the GPU work** (number of model pairs):

| Argument / setting | Effect |
|---|---|
| The policy: number of labels, `run_if`, gate threshold | more labels mean more pairs per gated paragraph (now about 13–15) |
| The keyword lists and markers | decide the keyword share, the biggest factor (1 % vs 10 % ≈ 4 h vs 1 day) |
| `--all-labels` | every label on every gated paragraph: about 2–3× more pairs. Only for sample runs |
| `--judge-model none` | about 20–40 % less GPU time, different decisions |
| `--uncertain-band` | narrower = fewer judge pairs |
| `--fast-model` | `deberta` (as fast model) or `bge-m3` are slower than `modernbert` |
| `--max-length` | longer pairs cost more (default 512 fits 2,000-character paragraphs) |
| `--topic-field` with `hint` / `trust` | subjects named by the corpus' field skip the model: fewer pairs |
| `--batch-size`, `--chunk-lines`, copies per GPU | same work, but how well the GPU is used (earlier answers) |

**Medium effect: changes CPU and disk work**:

| Argument | Effect |
|---|---|
| `--write-clean` | writes a second copy about the size of the input, compressed: more CPU and disk |
| `--compress none` | less CPU, but outputs 5–10× bigger |
| `--no-rewrite` | skips the place-name rewrite in the clean copy: a little less CPU |
| `--no-rules` | skips the cheap rules; can send more paragraphs to the models |

**No effect on speed:** `--review-as`, `--min-doc-chars`, `--id-field`, `--group-field`, `--overwrite`.

**The planned options** (`11_24_output_modes`), once built:
- **Simple mode** writes much smaller outputs (one decision per line, no scores per paragraph) and no clean copy. It
  saves disk and some CPU. **The model work is the same.**
- **Line unit** has the same model work: paragraphs are still scored, only the output is per line.
- **The non-English setting "remove"** (Arabic first): those paragraphs are decided without the model, unless
  `score_when_removed` is on. It saves GPU only if there is much Arabic text.

So: always do the sizing run with **exactly** the arguments of the real run.
